# Step 25 - 기획: 전체 조사결과 기반 (독립 검증 루프)

## 목표

검증된 전체 조사 증거와 주제 계약을 빠짐없이 반영한 기초 기획 스냅샷을 만들고,
작성자와 분리된 검증자가 근거 충실성을 판정한다. 새 자료를 수집하거나 다른 단계의
기획 파일을 덮어쓰지 않는다.

## 입력과 산출물

- 입력: `step_archive/TOPIC/TOPIC.md`
- 입력: `step_archive/step016_조사결과_chunk1.md`
- 입력: `step_archive/research-raw-step016-primary.txt`
- 입력: `step_archive/screenshots/research/step016-primary.png`
- 입력: `step_archive/outputs/step024_검증_r1.md`
- 필수 선행 항목: `step016`, `step024`
- 산출물: `step_archive/step025_planning_chunk1.md`
- 산출물: `step_archive/outputs/step025_검증.md`
- 네트워크: 사용하지 않는다.
- 시각 검토: 필요하지 않다.

## 실행 역할

가능한 경우 기초 기획 스냅샷 작성자 역할과 조사 반영 독립 검증자 역할을 나눈다.
작성자는 입력 근거로 기획을 만들고, 독립 검증자는 작성 산출물을 수정하지 않는다.
검증자는 원본과 기획을 처음부터 대조해 판정만 기록한다. 위임 기능을 사용할 수
없으면 현재 실행자가 두 역할을 명확히 분리해 순서대로 수행하고, 별도 역할을
위임했다고 기록하지 않는다. 어느 방식에서도 정상 권한 확인을 유지하고 자동
승인이나 권한 우회를 금지한다.

## 주제 계약을 가장 먼저 확인

어떤 기획 작업보다 가장 먼저 `step_archive/TOPIC/TOPIC.md`를 읽는다. `topic`,
`audience`, `interactive`, `real_world_apps`, `constraints`를 모두 추출해 변경하지 않는
검사표로 만든다. 값이 없거나 서로 모순되면 추정으로 채우지 않고 이 단계를
완료하지 않는다. 기획의 기능, 설명 수준, 상호작용, 사례와 기술 경계는 각 항목에
직접 연결되어야 한다.

`step_archive/outputs/step024_검증_r1.md`의 최종 판정이 근거 있는 `PASS`인지 확인한다.
보고서가 없거나 최종 판정이 `FAIL`이면 작업을 시작하지 않는다.

## 근거 기반 기초 기획

작성자는 16단계 조사 청크, 원본 텍스트, capture 경로와 24단계 충분성 판정을 모두
읽는다. 기능 범위, 사용자 흐름, 데이터 경계, Class 책임, 위험과 비목표를 정의한다.
각 사실과 결정에는 출처 파일, 청크 절 또는 capture 식별자를 붙인다. 사전 지식이나
근거 없는 보간을 사실처럼 쓰지 않는다.

플러그인의 `docs/ROUTING.md`를 읽고 독립 화면 목록·목적·진입 링크를 기획에 포함한다.
각 독립 화면은 공유·직접 접속 가능한 URL을 가져야 한다. 필터·대화상자와 독립 화면을
구분하고 실제 한 화면이면 하나만 선언한다. 이후 기획 스냅샷과 30단계 설계에 이
목록을 전달하며 검증자는 메뉴 아래 화면의 누락도 확인한다.

`step_archive/step025_planning_chunk1.md`는 이 단계만 소유하는 기초 기획
스냅샷이다. 첫 청크 manifest에 입력 digest, 포함 절, 결정별 출처와 전체 줄 수를
기록하고 파일을 500줄 이하로 유지한다. 범위가 한 파일에 들어오지 않으면 선언되지
않은 청크를 만들지 말고 범위를 재구성하거나 차단한다. 이후 단계는 이 파일을
덮어쓰지 않고 별도의 스냅샷을 만든다.

## 독립 검증 축

검증자는 조사 충실성 네 축을 각각 근거로 판정한다.

- 데이터 반영: 각 결정이 보존된 조사 데이터에서 나왔는가
- 누락: 중요한 패턴과 제약이 빠지지 않았는가
- 왜곡: 원본의 의미나 수치를 바꾸지 않았는가
- 출처 추적: 주요 사실과 결정이 정확한 입력까지 연결되는가

주제 충실성 네 축도 별도로 판정한다.

- 주제 일치: `topic`을 실제로 다루는가
- 타깃 적합성: `audience`에 난이도와 설명 방식이 맞는가
- 인터랙티브 충족: `interactive` 계약이 사용자 흐름에 반영됐는가
- 사례 반영: `real_world_apps`의 사례와 `constraints`가 결정에 반영됐는가

## bounded 검증 라운드

모든 라운드는 동일한 선언 보고서 `step_archive/outputs/step025_검증.md`에 라운드별 섹션으로
기록한다. 라운드마다 입력 digest, 여덟 판정 축, 발견 사항, 작성자의 보정,
재검증 결과를 남기며 최대 5라운드만 수행한다. 실패와 해결 이력은
`step_archive/outputs/step025_검증.md`에만 기록하고 외부 실행 제어 파일은 수정하지
않는다.

- `PASS`: 여덟 축이 모두 근거로 충족된 경우에만 완료한다.
- `FAIL`: 완료 증거가 될 수 없다. 작성자만 기획을 보정하고 검증자가 다시 판정한다.
- 항목을 건너뛰거나 해결된 것처럼 표시하지 않는다.
- 5라운드까지 `PASS`가 없으면 workflow를 차단하고 미해결 항목과 필요한 조치를
  같은 보고서에 기록한다.

## 최종 보완 증거 인계

24단계 최종 PASS 보고서의 보완 manifest와 통합 분석을 함께 읽는다. 채택한 원본·이미지의 실제 경로와 SHA-256, 24단계의 시각 검사 판정을 대조한다.
이 단계는 검증된 분석의 기획 반영과 provenance를 확인한다. 채택한 이미지의 새 시각 검토는 29단계에서 수행하며, 여기서 직접 이미지를 열어 검사했다고 기록하지 않는다.
원래 23단계 결론과 달라진 조사 축·대안은 24단계의 검증된 최종 분석을 따른다. 보완이 없으면 명시된 빈 manifest를 확인한다.
입력 digest와 결정 provenance에 채택한 보완 경로·hash를 기록하고 다음 기획·설계 산출물로 전달한다. 새 네트워크 수집이나 이전 증거 수정은 하지 않는다.

## 선택형 Jev 보조 검토

이 단계의 필수 절차는 네트워크 미사용 계약을 유지한다. Jev CLI는 사용자가 별도로
명시 호출하는 독립 보조 검토이며 workflow가 자동 실행하지 않는다. 기존 네트워크
계약이나 호스트 권한을 우회하는 예외로 해석하지 않는다.

사용자가 보조 검토와 선택한 내용의 외부 전송을 명시적으로 선택한 경우에만 플러그인
`docs/JEV-REVIEW.md`의 공통 CLI를 사용한다. 에이전트는 미지정 선택을 추정하지 않으며
현재 단계 도달이나 `TYPESAFE_API_KEY` 존재만으로 실행하지 않는다. 실제 호출에는
`run --allow-network`도 필요하다. `prepare`와 `inspect`는 오프라인이다.

입력 JSON에는 `step_archive/TOPIC/TOPIC.md` 안의 정확한 `topic_excerpt`, 그 안에
정확히 포함된 `requirements[].text`, 이미 선언된 `step_archive/step025_planning_chunk1.md`의
상대경로와 정확한 `planning[].excerpt`를 명시한다. 공개 또는 외부 전송이 허용된
비민감 내용만 선택해 stdin으로 전달하며 새 청크나 조사 자료를 자동 수집하지 않는다.

결과는 요구사항별 `met`·`unmet`·`insufficient_evidence`와 확률분포·confidence를 담는
보조 자료다. confidence는 실제 정답률이 아니며 한국어 정확도는 별도 검증이 필요하다.
timeout·인증·응답 오류는 `unverified`, 보고서 생성 후 원본 변경은 `stale`로 취급한다.
보고서는 `step_archive/outputs/jev-reviews/<sha256>.json`에 저장되며 재사용 전 `inspect`로
원본 해시를 확인한다. `current`여도 `review_status: unverified`이면 미검증이다.

독립 검증자는 이 자료를 참고하되 기존 필수 Acceptance, 조사·주제 충실성 판정 축과
완료 조건을 모두 수행한다. Jev 결과·종료 코드 0·`current`는 PASS나 완료 권한이 아니며,
필수 산출물·수락 증거와 workflow 상태·영수증을 대체하지 않는다.

## 완료 조건

- `base-planning-snapshot`: 주제와 조사 증거를 추적하는 기초 기획 스냅샷이 있다.
- `planning-verification-report`: 단일 보고서에 연속된 검증 라운드가 있다.
- `topic-fidelity`: 다섯 주제 필드와 네 주제 판정 축이 모두 충족된다.
- `general-research-provenance`: 모든 사실과 결정이 보존된 입력으로 추적된다.
- `planning-chunks-bounded`: manifest와 실제 파일이 일치하고 500줄 이하이다.
- `bounded-independent-review`: 독립 판정이 최대 다섯 번 안에 끝난다.
- `pass-verdict`: 최종 판정이 근거 있는 `PASS`다.

검증 결과와 두 산출물의 경로를 수락 증거로 제출하고 현재 단계에서 멈춘다.
workflow 상태와 영수증만이 이후 진행을 소유한다.
