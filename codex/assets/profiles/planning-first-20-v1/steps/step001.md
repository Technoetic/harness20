# Step 1 - 기획: 요구사항 기반 (독립 검증 루프)

## 목표

사용자 요청·명시적으로 제공된 자료와 주제 계약을 빠짐없이 반영한 기초 기획 스냅샷을 만들고,
작성자와 분리된 검증자가 근거 충실성을 판정한다. 새 자료를 수집하거나 다른 단계의
기획 파일을 덮어쓰지 않는다.

## 입력과 산출물

- 입력: `step_archive/TOPIC/TOPIC.md`
- 필수 선행 항목:
- 산출물: `step_archive/step001_planning_chunk1.md`
- 산출물: `step_archive/outputs/step001_검증.md`
- 네트워크: 승인된 Jev 선택 API만 허용한다. 일반 웹 탐색과 새 자료 수집은 사용하지 않는다.
- 시각 검토: 필요하지 않다.

## 실행 역할

가능한 경우 기초 기획 스냅샷 작성자 역할과 요구 반영 독립 검증자 역할을 나눈다.
작성자는 입력 근거로 기획을 만들고, 독립 검증자는 작성 산출물을 수정하지 않는다.
검증자는 원본과 기획을 처음부터 대조해 판정만 기록한다. 위임 기능을 사용할 수
없으면 현재 실행자가 두 역할을 명확히 분리해 순서대로 수행하고, 별도 역할을
위임했다고 기록하지 않는다. 어느 방식에서도 정상 권한 확인을 유지하고 자동
승인이나 권한 우회를 금지한다.

검증자에게 `workflow_profile`(`planning-first-20-v1`), 관리자가 확인한 `workflow_generation`,
현재 기획 시도 식별자 `planning_attempt`, TOPIC 입력 SHA-256 `topic_sha256`을 전달한다.
작성자는 각 청크 manifest에 이 네 값을 기록하고 호출자는 검증한 실제 값으로 인계를 구성한다.
호출자는 이번 시도에 실제 생성한 기획 청크의 명시 경로·SHA-256 목록만 전달한다.
검증자는 각 manifest의 네 값과 현재 파일 바이트를 인계에 대조하며 다른 실행의 기획·청크·
보고서를 탐색하지 않는다. 재시도는 같은 프로필·실행 세대·TOPIC digest 및 현재 기획 시도와의
연결이 확인된 자기 이전 라운드 기록의 명시 경로·SHA-256 목록만 전달한다.
출처가 확인되지 않은 기록은 사용하지 않고 현재 고정 입력과 이번 시도의 기획을 검증한다.
필수 요구 누락·충돌, 인계 연결 누락 또는 hash 불일치는 INCOMPLETE다.

## 주제 계약을 가장 먼저 확인

어떤 기획 작업보다 가장 먼저 `step_archive/TOPIC/TOPIC.md`를 읽는다. `topic`,
`audience`, `interactive`, `real_world_apps`, `constraints`를 모두 추출해 변경하지 않는
검사표로 만든다. 값이 없거나 서로 모순되면 추정으로 채우지 않고 이 단계를
완료하지 않는다. 기획의 기능, 설명 수준, 상호작용, 사례와 기술 경계는 각 항목에
직접 연결되어야 한다.


TOPIC은 초기화 관리자가 여섯 필드와 사용자 원문을 보존한 읽기 전용 입력이다.
Codex 관리자는 `state.topic_sha256`을 현재 TOPIC 입력 바이트와 자동 대조한다.
관리자의 무결성 검사가 실패하면 이 단계를 완료하지 않는다.
`decisions`와 `original_request`가 있으면 원문·명시 제약·기본값 표시를 함께 대조한다.
기본값을 새로운 사용자 결정이나 승인으로 해석하지 않는다. 필수 주제 필드의 실제 누락·모순·
원문 손실은 차단하며 TOPIC 바이트를 직접 고치거나 이전 단계 완료 기록을 만들지 않는다.
이 단계는 앞선 프리플라이트나 의존성 게이트 보고서를 요구하지 않는다.

## 현재 기획의 재시도 기록

새 실행의 첫 기획에는 이전 기획 단계가 없다. 고정된 TOPIC과 사용자가 명시적으로
제공한 자료만 입력으로 읽으며, 저장된 다른 프로필이나 이전 실행의 산출물을 찾아 읽지 않는다.
재시도일 때만 관리자가 확인한 `planning-first-20-v1`, 현재 `workflow_generation`
(`run_started_at` 또는 `workflow_id`에서 검증한 실행 세대), 현재 기획 시도와의 연결,
TOPIC 입력 digest가 모두 일치하는 자기 기획·검증 기록의 명시 경로를 읽는다.
출처가 확인되지 않은 기록은 사용하지 않고 현재 고정 입력으로 기획을 작성한다.
이전 실행의 실패 패턴이나 완료 증거를 현재 실행의 선행 조건이나 검증으로 가져오지 않는다.

## 근거 기반 기초 기획

작성자는 TOPIC과 사용자 요청, 명시적으로 제공된 자료를 읽는다. 기능 범위, 사용자 흐름, 데이터 경계, Class 책임, 위험과 비목표를 정의한다.
각 사실과 결정에는 출처 파일, 청크 절 또는 요구 ID를 붙인다. 사전 지식이나
근거 없는 보간을 사실처럼 쓰지 않는다.

플러그인의 `docs/ROUTING.md`를 읽고 독립 화면 목록·목적·진입 링크를 기획에 포함한다.
각 독립 화면은 공유·직접 접속 가능한 URL을 가져야 한다. 필터·대화상자와 독립 화면을
구분하고 실제 한 화면이면 하나만 선언한다. 이후 기획 스냅샷과 2단계 설계에 이
목록을 전달하며 검증자는 메뉴 아래 화면의 누락도 확인한다.

`step_archive/step001_planning_chunk1.md`는 이 단계만 소유하는 기초 기획
스냅샷이다. 첫 청크 manifest에 입력 digest, 포함 절, 결정별 출처와 전체 줄 수를
기록하고 파일을 500줄 이하로 유지한다. 범위가 한 파일에 들어오지 않으면 선언되지
않은 청크를 만들지 말고 범위를 재구성하거나 차단한다. 이후 단계는 이 파일을
덮어쓰지 않고 별도의 스냅샷을 만든다.

## 독립 검증 축

검증자는 요구 충실성 네 축을 각각 근거로 판정한다.

- 데이터 반영: 각 결정이 보존된 제공 자료에서 나왔는가
- 누락: 중요한 패턴과 제약이 빠지지 않았는가
- 왜곡: 원본의 의미나 수치를 바꾸지 않았는가
- 출처 추적: 주요 사실과 결정이 정확한 입력까지 연결되는가

주제 충실성 네 축도 별도로 판정한다.

- 주제 일치: `topic`을 실제로 다루는가
- 타깃 적합성: `audience`에 난이도와 설명 방식이 맞는가
- 인터랙티브 충족: `interactive` 계약이 사용자 흐름에 반영됐는가
- 사례 반영: `real_world_apps`의 사례와 `constraints`가 결정에 반영됐는가

## bounded 검증 라운드

모든 라운드는 동일한 선언 보고서 `step_archive/outputs/step001_검증.md`에 라운드별 섹션으로
기록한다. 라운드마다 입력 digest, 여덟 판정 축, 발견 사항, 작성자의 보정,
재검증 결과를 남기며 최대 5라운드만 수행한다. 실패와 해결 이력은
`step_archive/outputs/step001_검증.md`에만 기록하고 외부 실행 제어 파일은 수정하지
않는다.

- `PASS`: 여덟 축이 모두 근거로 충족된 경우에만 완료한다.
- `FAIL`: 완료 증거가 될 수 없다. 작성자만 기획을 보정하고 검증자가 다시 판정한다.
- 항목을 건너뛰거나 해결된 것처럼 표시하지 않는다.
- 5라운드까지 `PASS`가 없으면 workflow를 차단하고 미해결 항목과 필요한 조치를
  같은 보고서에 기록한다.

## 제공 API 계약과 미확정 요구

API를 사용하는 경우 사용자가 제공한 명세·자료 또는 명시적으로 선언한 계약에서
target, version, schema, auth, rate-limit, error, retry 정책을 추출한다. 요구 ID와
출처 파일·절·SHA-256을 연결한다. 누락된 필수 항목은 missing requirements로 남겨
차단하거나 명시적인 계약 결정을 받는다. 대상이 없으면 근거 있는 N/A를 기록한다.
추정한 최신 외부 사실이나 실행하지 않은 검증을 PASS로 기록하지 않는다.
테스트 결과는 선언한 계약의 동작 증거이며 외부 사실의 현재성을 증명하지 않는다.

## Jev 의미 체크포인트

TOPIC의 요구와 기획의 대응 문장이 준비되면 선택한 요구가 명시적으로 반영됐는지 묻는다. 기존 `scripts/jev-review.mjs`와 `docs/JEV-REVIEW.md`는 버전 1 호환 경로다. 새 자동 검토는 일반 helper만 사용하며 두 어댑터를 중복 호출하지 않는다.

현재 작업에서 Jev 사용과 선택한 발췌문의 외부 전송이 승인된 경우 호스트가 자동 호출한다.
기존 승인이 해당 범위를 포함하면 재확인하지 않는다. 단계 도달이나 `TYPESAFE_API_KEY` 존재는 승인이 아니다.
승인이 없거나 서비스가 불가하면 이유를 기존 단계 보고서에 기록하고 독립 검증을 계속한다.

신뢰한 플러그인의 `node "<plugin-root>/scripts/jev-judge.mjs" prepare --workspace ROOT --input -`로 준비한다.
재사용 전 `inspect --workspace ROOT --report PATH`의 상태와 현재 prepare의 `request_hash`, `policy_hash`, `input_hash`, `sources`를 모두 대조한다.
새 호출은 동일 JSON으로 `run --workspace ROOT --input - --allow-network`를 실행한다.
변하지 않은 입력에는 한 배치만 호출하는 호스트 정책을 적용하며 전역 하드 쿼터로 해석하지 않는다.
`unverified`·`stale`는 판정 근거로 쓰지 않고 abstain·낮은 confidence는 호스트가 원본을 검토한다.
승인된 선택 API 예외는 일반 웹 탐색이나 새 자료 수집을 허용하지 않는다.

입력 파일·발췌문 범위, 동의·중복 방지·보고서 검사는 `docs/jev-checkpoints.md`를 따른다.
기존 독립 검증·Acceptance·실제 검사와 완료 writer는 유지한다. Jev 결과나 `current`는 PASS 또는 완료 권한이 아니다.

## 완료 조건

- `provided-api-contract`: 제공·선언 계약의 필수 API 항목을 추적하고 누락·미확정은 차단했다. 외부 API가 없을 때만 근거 있는 N/A다.

- `base-planning-snapshot`: 주제와 요구사항 근거를 추적하는 기초 기획 스냅샷이 있다.
- `planning-verification-report`: 단일 보고서에 연속된 검증 라운드가 있다.
- `topic-fidelity`: 다섯 주제 필드와 네 주제 판정 축이 모두 충족된다.
- `requirements-traceability`: 모든 사실과 결정이 보존된 입력으로 추적된다.
- `planning-chunks-bounded`: manifest와 실제 파일이 일치하고 500줄 이하이다.
- `bounded-independent-review`: 독립 판정이 최대 다섯 번 안에 끝난다.
- `pass-verdict`: 최종 판정이 근거 있는 `PASS`다.

검증 결과와 두 산출물의 경로를 수락 증거로 제출하고 현재 단계에서 멈춘다.
workflow 상태와 영수증만이 이후 진행을 소유한다.
