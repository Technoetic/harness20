# Evaluator 스킬 (생성자-평가자 패턴)

## 핵심 원칙
**작성 에이전트 != 검증 에이전트**
같은 에이전트가 작성하고 스스로 통과 판정하는 것을 금지한다.

필수 acceptance와 증거의 통과 여부가 완료 판정을 결정한다. 32/40 루브릭은 참고 점수이며,
필수 검사 실패를 상쇄하거나 미관·선호만으로 완료를 차단하지 않는다.

## 트리거 조건
- 각 Step 파일 내부에 `# EVAL` 또는 `평가자 실행` 지시가 명시된 경우
- Step 번호 범위에 의존하지 않는다 — Step 파일이 직접 호출하는 방식이 기준

> **Why:** Step 번호 하드코딩 시 Step 파일이 추가/재번호되면 트리거 누락 발생

## 평가 프로토콜

### 0단계: 필수 기준 확인

호출한 Step/SPEC의 필수 acceptance, 검사 명령, 필요한 스크린샷과 기타 증거를 확인한다.
필수 선행 입력이 없거나 필요한 검사·증거를 확보할 실행 기능이 없으면 `INCOMPLETE`로 기록하고 현재 Step을 차단한다.
이번 평가에서 만들 스크린샷은 다음 절차에서 확보하며, 최종 판정 시 필수 증거의 누락을 확인한다.
필수 기준을 평가 도중 완화하거나 실패 항목을 참고 의견으로 강등하지 않는다.

### 1단계: 구현물 스크린샷 촬영

Step 3이 `step_archive/outputs/browser-backend.json`에 고정한 브라우저 백엔드(잠금 파일이 없으면 사용 가능한 백엔드: Playwright 또는 Aside CLI — `docs/BROWSER-TOOLS.md`의 절차표 참조)로 현재 구현 상태를 3가지 뷰포트(desktop 1920x1080, tablet 768x1024, mobile 390x844)로 캡처한다. Aside에서는 고정 탭 뷰포트 대신 해당 크기의 iframe 호스트 페이지와 `clip` 스크린샷을 쓴다.

저장 경로: step_archive/screenshots/eval-rN-{viewport}.png

스크린샷은 반드시 `fullPage: true` 옵션으로 전체 페이지를 캡처한다.

**브라우저 백엔드 실패 시 폴백(어느 백엔드든 동일):**
스크린샷 촬영이 실패해도 확보된 증거로 진단을 남길 수 있다.
- 디자인 충실도 항목은 0점으로 기록하고 사유를 명시
- 나머지 3개 항목(기능 완성도, 코드 품질, 성능)은 코드 분석 기반으로 평가 진행
- 평가 결과에 `⚠️ 스크린샷 없음 - 코드 분석 기반 평가` 표기
- 이 평가는 필수 시각 검증을 대체하지 않는다. 필수 스크린샷을 촬영하거나 직접 열어 볼 수 없으면 `INCOMPLETE`이며 다음 Step으로 진행하지 않는다.

### 2단계: 평가자 에이전트 스폰 (sonnet 모델)

평가자 에이전트에게 전달할 프롬프트:

> 너는 독립 평가자다. 코드를 수정하지 않는다. 판정만 한다.
> **절대 규칙: `.claude/` 디렉토리에 어떤 파일도 생성하지 않는다. 출력은 반드시 step_archive/outputs/ 에만 저장한다.**
> `progress.json` 등 공유 workflow 상태를 직접 수정하지 않는다. 기존 workflow writer만 완료 상태를 반영한다.
>
> 1. 원본 참조 자료를 읽는다:
>    - step_archive/에서 해당 Step의 조사 결과 청크 파일
>    - step_archive/screenshots/research/ 의 원본 스크린샷
>    - 호출한 Step/SPEC의 필수 acceptance와 필수 검사 결과. 검사 명령·종료 코드·증거 경로를 확인한다.
>
> 2. 구현 스크린샷을 읽는다:
>    - step_archive/screenshots/eval-rN-*.png
>
> 3. 이전 라운드 평가 결과를 읽는다 (있으면):
>    - step_archive/outputs/eval_rN-1.md
>    - 이전 FAIL 항목의 수정 여부 확인
>    - **점수 추이 비교**: 이전 라운드 총점과 현재 총점을 비교한다
>      - 점수가 하락하면 `⚠️ 점수 퇴보 감지 (이전 XX/40 → 현재 YY/40)` 경고를 결과에 명시
>      - 퇴보 원인 항목을 특정하여 피드백에 포함
>
> 4. 필수 판정과 참고 점수를 분리한다:
>    - 필수 검사·증거가 모두 통과하고 미해결 `Critical`/`Important` finding이 없을 때만 `PASS`다.
>    - 필수 기준 위반은 `FAIL`이며, 필수 입력·증거·실행 기능 부재 또는 라운드 중단 조건 충족은 `INCOMPLETE`다.
>    - `Critical`/`Important` finding은 요구사항·기능·접근성·보안·선택된 디자인 토큰과 관찰 증거에 연결한다.
>    - 근거 없는 미관·선호 의견은 `advisory`다. 필수 실패를 참고 의견으로 강등하지 않는다.
>
>    참고 루브릭:
>    - 기능 완성도 (0-10): 요구사항 대비 구현 비율
>    - 디자인 충실도 (0-10): 원본 참조 대비 시각적 일치도
>    - 코드 품질 (0-10): 린팅/포매팅/타입 안전성
>    - 성능 (0-10): 로드 시간, DOM 복잡도
>
> 5. 결과 저장: step_archive/outputs/eval_rN.md
>    - 총점 32/40 이상: 참고 목표 충족. 필수 검사·증거 실패가 있으면 `PASS`가 아니다.
>    - 총점 32 미만: 참고 목표 미달과 구체적 의견 기록. 필수 검사를 모두 통과했다면 점수만으로 `FAIL` 또는 재시도를 요구하지 않는다.
>    - 비밀값·개인정보·원시 로그 대신 필요한 요약과 프로젝트 상대 증거 경로를 기록한다.
>
> 형식:
>
> ## 평가 결과 Round N
> - Step: 현재 Step 번호
> - 필수 검사: 기준별 PASS/FAIL/INCOMPLETE + 명령·종료 코드·증거 경로
> - 필수 시각 검사: 직접 확인한 스크린샷 경로 또는 차단 사유
> - 기능 완성도: X/10
> - 디자인 충실도: X/10
> - 코드 품질: X/10
> - 성능: X/10
> - 참고 총점: XX/40 (목표 32/40)
> - 판정: PASS/FAIL/INCOMPLETE (필수 검사·증거와 중단 조건 기준)
>
> ### 필수 finding (있으면)
> 1. 중요도 + 필수 기준: 구체적 설명 + 증거 경로 + 수정 방향 + 해결/미해결 + 재검증 결과
>
> ### 참고 의견 (있으면)
> 1. advisory: 미관·선호 제안
>
> ### 중단 시 인계
> - 차단 원인 / 시도한 수정 / 남은 필수 finding / 다음 안전한 조치

### 3단계: 판정 처리
- **PASS**: 필수 검사·증거 통과와 미해결 `Critical`/`Important` 부재를 확인한 뒤 기존 Step 완료 절차로 복귀
- **FAIL**: 필수 finding을 구현 에이전트에 전달하여 수정 후 독립 재평가 (전체 최대 5라운드)
- **INCOMPLETE**: 결과 보고서를 남기고 현재 Step에서 중단. 완료를 보고하거나 다음 Step으로 진행하지 않는다.
- 참고 의견만 남은 경우 선택적 개선으로 기록한다. 필수 검사를 통과했다면 점수나 선호만으로 추가 라운드를 시작하지 않는다.

## 라운드 제한
- 최초 평가를 1라운드로 세며 수정·재평가를 포함해 전체 최대 5라운드다. 수정 방식이나 평가자 변경으로 회차를 초기화하지 않는다.
- 동일 필수 finding이 3라운드 연속 미해결·무진전이면 일찍 중단하고 `INCOMPLETE`로 기록한다. 해당 항목을 스킵해 통과시키지 않는다.
- 5라운드 뒤에도 필수 실패 또는 미해결 `Critical`/`Important`가 있으면 `INCOMPLETE`다. 남은 finding과 다음 안전한 조치를 `step_archive/outputs/eval_rN.md`에 기록하고 현재 Step에서 멈춘다.
- `progress.json`의 `failed_steps` 등 공유 상태를 직접 갱신하지 않는다. 보고서는 기존 Step의 결과 증거이며 자체적으로 완료·재개 권한을 부여하지 않는다.
