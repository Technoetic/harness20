# harness20 v4.1.0 — verified experience memory

This release adds optional local memory for sanitized failures, QA-backed repair
lessons and later observations. Explicit CLIs retrieve bounded, digest-pinned
context and validate declared work units, reads and checkpoints. Workers can
inspect advice; the orchestrator registers it only after actual repairs and
current recorded QA evidence.

The existing state manager, TOPIC binding, guards, acceptance contracts, QA and
receipts retain authority. Advice does not execute commands, grant approval,
clear failure counts or complete a step. Existing twenty-, thirty-six- and
fifty-stage workflows keep their original meanings and evidence. Historical
workflows without a supported generation return an explicit unsupported memory
result while normal execution remains available.

## Added capabilities

- Immutable lessons and observations with scope, validity, related evidence,
  supersession, retirement and separate outcome denominators.
- Bounded provenance checks and a cooperative lifecycle lock; missing,
  abandoned or incomplete lifecycle proof fails closed without bulk archive
  scans or automatic lock theft.
- Explicit selected-source retrieval using BM25, rank fusion and at most two
  hops of declared links. Mandatory scope and blockers must fit the complete
  serialized response budget.
- Request-wide bounded reads and strict stdin JSON commands; selected source
  hashes, UTF-8 boundaries and path policy are checked before use.
- Work-unit, read-ledger and checkpoint declarations with current file hashes.
  Validation does not prove actual tool history or execute declared commands.
- Paired offline synthetic later-action evaluation and temporary-workspace
  integration tests for real candidate repair, QA, fresh-process recovery,
  poisoned advice and preservation of state, events and receipts.

Full schemas, commands, limits and the nine scoped paper/project references are
in [experience-memory.md](../experience-memory.md). The references guide selected
engineering patterns; the release does not reproduce their full systems or
reported benchmark results. No new provider, network service, dependency,
installed settings change or automatic SessionStart memory injection is added
by the memory feature.

## Upgrade and host use

Update the existing `harness20` plugin through the host's native plugin manager.
Retain previous caches for rollback and preserve existing activation scopes and
explicit project disable settings. Do not reactivate older `harness36` or
`harness50` plugins alongside it. Existing workflow state is not initialized or
reset as part of an update.

Start a fresh Claude Code or Codex session after updating. Native hook review and
manual trust remain host requirements; changed hook hashes require review
again. Installation and preflight do not fabricate an AfterTrust receipt or
grant execution permission. Existing generated-HTML isolation and provider/OS
limits remain described in [SECURITY.md](../SECURITY.md).

legitimate cases in both arms, with recurrence 2/3 memory-off and 0/3 memory-on.
Executed unsafe actions were zero in both arms; each had one attempted unsafe
action. These fixture measurements are not real-model, business-performance or
paper-benchmark results.
