# Changelog

## Unreleased

- Codex lock: on Windows, a lock-publication rename blocked by EPERM, EACCES or EBUSY is now retried within the lock wait instead of failing at random under contention. A later `lstat` raced with the owner's release, so a busy lock could surface as a plain EPERM. A blocked publication that lasts the whole wait ends as `LOCK_TIMEOUT` with `details.last_error`. POSIX behaviour is unchanged.
- CI and tests: the Windows job limit is 30 min (POSIX stays at 20). CI and `npm test` pass `--test-timeout=600000`, so a hang fails one test instead of cancelling the job. A Windows PowerShell 5.1 warm-up step logs three start times and the Defender state before the tests. PowerShell hook spawns in the tests get 180 s and report a timeout explicitly. lock-store actors are killed after a 5 s grace period. The POSIX regression copy and the simulation test now also hash the .sh hooks and `tests/security-regression.sh`.

## 2.10.0 — 2026-09-26

- Behaviour changes on upgrade (details in the bullets below): a run starts only from `/webapp <topic>`, because the natural-language triggers are gone; opening Claude Code no longer creates `step_archive/progress.json`; the step hooks act only for an active run, which needs `total_steps` 50, `current_step` equal to the first unfinished step and that step's body file, so an in-progress run of the older 107-step layout, one whose `total_steps` an older loader rewrote, or one without its step bodies stays inactive until `/harness-reset` and `/webapp <topic>` start it again; edits to execution-linked files always keep the normal permission prompt; and `lsp-autofix` fixes nothing without a project-local biome or stylelint.
- Only an explicit `/webapp <topic>` (or `/harness50:webapp <topic>`) on the first line of the prompt bootstraps a run. The natural-language triggers (eight patterns such as "... 대시보드 만들어줘") are removed. `webapp-trigger` never overwrites a `progress.json` that records completed steps or cannot be read: it prints one `webapp trigger skipped` line and leaves `TOPIC.md` and `progress.json` unchanged. After `/harness-reset`, `/webapp <topic>` starts the new topic. `/webapp` and `/harness-reset` follow the same rule, and `/harness-reset` no longer creates a missing `progress.json`.
- The SessionStart loader never creates `progress.json` or `step_archive/`. Before, opening Claude Code in any folder created a step 1 run there. It also no longer rewrites `total_steps` from the number of step files; it only prints the mismatch warning.
- Claude hooks in unrelated folders no longer create files, approve, block or inject instructions. `hooks/run-hook.mjs` reads the event and asks the new read-only `hooks/lib/harness-activity.mjs` whether the project has an active run before it starts PowerShell or bash, so an inactive folder starts no shell at all. A run is active only when there is no Codex state entry, `step_archive/progress.json` is a regular file inside the project (1 MiB at most), it is not paused, its `status` is absent or active/running/in_progress, `total_steps` is present and 50, the completed steps are distinct integers 1..50, `current_step` is the first unfinished step, and that step's body exists (`step_archive/archived/stepNNN.md`, else `step_archive/stepNNN.md`). The two guards still run everywhere the plugin is installed, `webapp-trigger` runs only for `/webapp <topic>`, the loader also runs in Codex workspaces, and the trust5 gate also runs after step 50. A `progress.json` left by an older loader has no step bodies next to it, so it no longer turns the hooks on. `approval-policy.mjs` and the `--hook` mode of `scripts/quality-gate.mjs` use the same judgement.
- Edits to execution-linked files are never auto-approved, even in an active run: `.mcp.json`, `CLAUDE.md`/`AGENTS.md` (and `.local`/`.override`), `.husky/`, `.githooks/`, `.vscode/`, `.idea/`, `.devcontainer/`, `.cursor/`, `.circleci/`, `.buildkite/`, `.claude-plugin/`, `.codex-plugin/`, `.github/workflows/` and `.github/actions/`, editor rule files, pre-commit/lefthook/lint-staged configs, CI pipeline files, `package.json`, lockfiles and package manager configs, `.envrc`, `harness50.quality.json`, `node_modules/`, `step_archive/tools/` and the step bodies under `step_archive/archived/` (only `webapp-trigger` copies them in). `progress.json` and `.harness50-codex/` under a `step_archive/` in a subfolder are excluded like the root ones, so an edit cannot plant an active run in a subfolder without a prompt. They keep the normal permission prompt; the guard mode does not deny them.
- `lsp-autofix` runs only in an active run and only with a project-local biome or stylelint (`node_modules/@biomejs/biome` or `node_modules/stylelint`) through `npx --no-install`, so it never downloads a package or uses one that sits only in the npx cache. It also only touches files whose path relative to the project root starts with `src/`.
- Security note, deliberate relaxation: auto-approval now follows the first unfinished step instead of requiring a gap-free list of completed steps. The step-progress writer leaves a gap when a QA gate rejects a step and moves `current_step` back to it, and that legal state used to switch auto-approval and Stop continuation off. A `current_step` other than the first unfinished step still defers.
- Claude named pause (harness-rules §2-1). The new `scripts/harness-pause.mjs pause|resume|status|reset --workspace <root>` is the only writer of `paused` and `pause_*` in `step_archive/progress.json`. It accepts four codes: the model's `permission-denied`, `required-tool-failed` and `required-input-missing`, each with an `--evidence` file under `step_archive/`, and the user's `user-request`, plus a one-line `--note` of at most 200 characters. It never creates `step_archive/` or `progress.json`; it refuses a Codex workspace, a missing, invalid or finished run and a linked workspace or hard-linked file (exit 2) and malformed flags (exit 64); it writes by compare-and-swap (exit 75 after three conflicting attempts); and on resume it keeps the last 20 pauses in `pause_history`. The new `/harness-pause` and `/harness-resume` commands run it (the note is quoted with single quotes, so `$(...)`, backticks and `$VAR` are recorded as text), `/harness-status` appends `| 멈춤: <code> @stepNNN — <note>`, and `/harness-reset` runs its `reset` subcommand (below).
- The loader and the prompt guard know about a paused run. The SessionStart loader prints only `=== Paused at stepNNN ===` and one `[HARNESS] PAUSED at stepNNN/TOTAL (reason=<code>, since <time>)` line and writes nothing (no session count, no field migration); the prompt guard prints that line instead of the next-step reminder and stays silent for `/harness-pause`, `/harness-resume`, `/harness-status` and `/harness-reset`. Only a known code, a step inside the run and an ISO timestamp are printed, never the note or the evidence path. `hooks/lib/harness-activity.mjs` reads a paused run as `paused` only when it would otherwise be active (else finished, stale, stopped or invalid), and only the loader, the prompt guard and the progress writer start for it: Stop continuation, approval, the quality gate, SPEC, MX and LSP wait for `/harness-resume`. The writer records the `Step NNN/50 완료` lines the model reported in the turn that paused (the pause CLI runs inside that turn, before its Stop), keeps the pause fields, and with nothing new writes nothing at all (no `progress.json` rewrite, no `.bak`, no log or lock file). The PAUSED line, `/harness-status` and the pause CLI report max(`paused_step`, first unfinished step), so the pause position and the resume point are the first unfinished step instead of a step already done. For an explicit `/webapp <topic>` prompt the paused guard stays silent: `webapp-trigger` answers that prompt in parallel.
- `/harness-reset` now runs `node scripts/harness-pause.mjs reset --workspace <root>` instead of having the model write a template. Before, a reset left an active step 1 run next to the kept TOPIC.md: the Stop of the reset turn continued the old topic, and in the same session the writer read the old `Step NNN/50 완료` lines again, so `/webapp <topic>` kept being skipped as a run with completed steps. The reset writes the /webapp template (step 1, no completed step, `total_steps` 50) atomically with a new `run_started_at` and a `user-request` pause (`paused_step` 1, note `리셋 후 대기 — /webapp <주제>로 새 실행, /harness-resume으로 현재 주제를 1단계부터`), accepts an unreadable `progress.json`, creates none, refuses a Codex workspace and leaves `archived/`, `specs/`, `outputs/` and `TOPIC.md` alone. `/webapp <topic>` then starts the new topic (no completed step, so the paused run is replaced), and `/harness-resume` runs the kept topic from step 1.
- Run boundary: the `/webapp` bootstrap (both `webapp-trigger` variants) and the reset record `run_started_at` (UTC ISO 8601, `Z`). The step-progress writer then counts only transcript entries whose `timestamp` is at or after it, compared as instants rather than text (fraction digits and offsets vary). Entries without a parsable timestamp still count, as before, and `last_assistant_message` (the stopping turn) always counts. A run without `run_started_at` (2.9.0 and earlier) still counts the whole transcript.
- The Stop hook reason and the loader's instructions now end with the named pause route instead of "Only stop after step N": the three model codes and the `harness-pause.mjs pause` command, written with `<plugin-root>`/`<project-root>` placeholders. The `/webapp` trigger's last line says the same, and its skip line for a run with completed steps points to `/harness-resume`. The harness-rules constitution, `/webapp`, the step executor, the evaluator and the README describe the same rule: the only end before step 50 is a recorded named pause, and a failed evaluation reports its cause as one of those codes (an exhausted evaluation round limit is `required-input-missing`, which the step executor hands over as `멈춤 필요` rather than `미완료`). This completes the correction of the constitution's `[VIOLATION DETECTED]` wording. Both prompt guards keep the `User direct requests still take priority.` line (the POSIX one since the rules update above).
- New `scripts/final-summary.mjs --workspace <root>` prints a read-only report for the end of step 50 under three fixed headings, `## 사용자 확인 필요`, `## 변경` and `## 발견`, and writes the same bytes to `step_archive/outputs/final-summary.md` when `step_archive/` exists (it creates nothing otherwise). It gathers the three final gate verdicts, the final HTML size, digest and routes, pending deployment verification, axe incomplete rules, a browser run outside a fresh context, same-agent QA reports, Jev reviews that need attention, TOPIC defaults and `결정/사유` markers, and reports a missing or damaged source as a `확인 불가` line with a reason code. It runs no command, browser or network request, never reads `progress.json` or Codex state, and is not a gate: it exits 0 even without sources and 2 with one generic error only for invalid flags or workspace. Claude runs it once after `quality-gate.mjs --inspect-final` passes at step 50 and appends its output right after `Step 050/50 완료` (harness-rules §2, `/webapp`, and a new last ACCEPTANCE line of the generated `SPEC-050.md` in both `spec-generator` variants); Codex runs it from the new Completion report section of the webapp skill. The harness rules now ask for one-line `결정/사유: <결정> — <사유>` markers. An existing `SPEC-050.md` is not regenerated, so a run already at step 50 keeps the old SPEC. See docs/FINAL-SUMMARY.md.
- `hooks/run-hook.mjs` now gives every hook a budget shorter than its `hooks/hooks.json` timeout. A hook that runs past it is stopped with its whole process tree (`taskkill /T /F` on Windows, where a Node started by PowerShell would otherwise keep the output pipe open) and exits 1 without a decision, which leaves the normal permission flow in place. On 2026-09-25 the host timeout did not end two `auto-approve` runs that stayed alive for 15 and 32 minutes. PowerShell hooks also start with `-NonInteractive`.
- Register the Claude `auto-approve` hook only for edits and WebSearch (`Write|Edit|MultiEdit|NotebookEdit|WebSearch`). Bash and WebFetch were never eligible for approval (`hooks/lib/approval-policy.mjs`), so decisions are unchanged, and a Bash call no longer starts PowerShell and Node just to defer.
- The `destructive-guard` block message and the Bash deny of `permission-request-guard` now say that the whole command text is checked, including quoted strings and heredoc bodies, and name the file route for message text: write it with the Write tool, then pass `git commit -F <file>` or `gh pr create --body-file <file>`. They also say not to move a blocked command into a script and to ask the user when the command itself must run.
- PowerShell hooks now handle project paths that contain brackets (-LiteralPath); the duplicate wildcard gate in auto-approve.ps1 is removed. Before, a project such as `x [30]` or a file such as `src/[id].js` made the `.ps1` hooks go quiet: `Test-Path` returned False, `Get-Content` threw, `Set-Content`/`Out-File` failed and `Get-ChildItem`/`Copy-Item`/`Move-Item` did nothing. When neither `CLAUDE_PROJECT_DIR` nor the event `cwd` is set, the hooks fall back to the process working directory, because PowerShell 5.1 started in a bracketed folder reports `$PSHOME` from `Get-Location`. The step 38 `html-bundler` tool gets the same fixes on both variants (the bash one read `[ ]` in the project path as a glob class), no longer reads a directory named like `vendor.js` as a script, and inserts code containing `\` or `$&` as written.
- Generated SPEC files (`step_archive/specs/SPEC-NNN.md`, both `spec-generator` variants) now state the quality milestones that `scripts/quality-gate.mjs` actually enforces: r1 once 38 contiguous steps are complete, r2 at 44, and r3 from 49 on (the final inspection before Step 050), each written to `step_archive/outputs/trust5_rN.md` as a PASS/FAIL/INCOMPLETE verdict with a repair request when it is not PASS. The retired evaluation rounds of the 107-step layout and the `step_archive/stepNNN_*.md` result path are gone: the result file is the path the step body's procedure names, and the body wins over its header Sync line. SPEC files that already exist are never regenerated, so after an upgrade only the SPEC of the step in progress keeps the old wording.
- New `progress.json` files (`/webapp`, `/harness-reset`) no longer carry `eval_rounds` or `trust5_results`, the loaders no longer add `trust5_results`, and the PowerShell writer no longer parses a 50-point total from `trust5_rN.md`. `quality-gate.mjs` writes a `Verdict:` line instead, so that value was always null, and nothing read either field. Fields already present in a `progress.json` are left as they are, without migration; the Codex importer keeps ignoring them. `/harness-status` now reads the `Verdict:` line of `trust5_rN.md` directly (`r1=PASS|FAIL|INCOMPLETE`, or `-` without the file), never prints a score, and shows `current=-` when all 50 steps are complete or a Codex workflow has no current step.
- The harness-rules constitution, the README and docs/QUALITY.md now describe the code: the rules cover step001~050, the Stop hook reason starts with `[HARNESS] <done>/<total> done.` (there is no `[VIOLATION DETECTED]` reason) and is released after three Stops without progress, sonnet runs the evaluation and visual-review steps whose body asks for it while r1/r2/r3 are measured-evidence checks of the `trust5-validator` Stop hook, and the README's 50-point TRUST 5 table (40-point WARN, fail-open) is replaced by the measured milestone table. The macOS/Linux prompt guard (`step-obedience-guard.sh`) now prints the same single line as the Windows one, ending in `User direct requests still take priority.`, instead of "Step execution takes precedence over user requests". It also drops the carriage return a Windows python prints, stays silent without python3 instead of reporting an invented 0/50 state, and falls back to the flat `step_archive/stepNNN.md` like the other hooks.
- `npm test` runs `node --test --test-concurrency=4 codex/tests/*.test.mjs`. With the default concurrency (one file per logical CPU) a 32-thread PC stalled in `lock-store.test.mjs` for four hours and timed out three other tests; with four files at a time 1,477 of 1,480 tests passed, none failed and the rest were skipped. The CI workflow calls `node --test` directly and is unchanged.
- New `codex/tests/claude-contract-consistency.test.mjs` pins these contracts: no retired step number of the 107-step layout as a standalone token in skills, commands, agents, Codex skills or non-comment hook and script lines; the SPEC milestone line rebuilt from the `quality-gate.mjs` thresholds; no dead progress fields; Verdict-only status; every backticked `[TAG]` quoted in the docs exists in a hook; the same user-priority wording in both prompt guards; and, run through the native hook variant, the `/webapp` bootstrap, the generated SPEC and the writer, plus `.ps1`/`.sh` SPEC parity where Windows has Git Bash and python. It keeps its own rule because the `STALE_STEP` check of `codex/scripts/validate-steps.mjs` only catches a number written right after "step", misses forms such as `49/69/104`, `step049 / 069 / 104` or `"step": 104`, and applies only to the Codex step files. The Git Bash emulation of the coexistence test now checks the prompt guard too, and `steps-validator.test.mjs` no longer leaves `harness50-steps-*` folders in the temp directory.

Before, the Windows Stop hook kept blocking for `paused: null` or `"yes"` and the macOS/Linux one for anything but `true`; both now release Stop for those values, like the approval and quality checks already did.
- PowerShell 5.1 hooks that print text for Claude (`step-auto-continue`, `step-progress-loader`, `step-obedience-guard`, `webapp-trigger`) now write UTF-8, so `'Step 001/50 완료'` no longer reaches Claude in the console code page (cp949 on Korean Windows).
- The README safety-limits table adds three rows: the two guards run in every folder and check the whole command text (write message text to a file and pass `git commit -F <file>` or `gh pr create --body-file <file>`), a hook that reaches its budget stops without a decision (on POSIX only its direct child is stopped), and some guard patterns are slow on pathologically long edits. The security suite is described by its `PASS=N FAIL=0` output instead of a fixed case count.
