## 최종 조사 기준

`step_archive/outputs/step024_검증_r1.md`의 최종 PASS manifest와 통합 분석을 먼저 읽는다.
비교 기준은 기존 참고 이미지와 최종 manifest에서 채택한 보충 이미지·조사 축을 모두 포함한다.
검증자는 보충 원문·스크린샷도 직접 열어 확인한다. 기존 glob에 없는 보충 이미지를 누락하거나
보충 전에 부족하다고 판정된 Step 23 결론만으로 비교 기준을 되돌리지 않는다.

## QA 완료 증거 (필수)

각 시도 시작에 `inspect --workspace "<project-root>" --step 40`으로 이전 실패를 확인한다.
수정과 필요한 build를 마친 뒤 검증 전에 `snapshot`을 만든다. 실제 소스·설정·검증 대상
산출물과 본문의 모든 필수 검사(화면·viewport·상태 조합 포함)를 명시한다.
검증자의 실제 관찰과 스크린샷·실행 결과를 `record`로 기록한 뒤 다시 `inspect`한다.
`status=current`와 `verdict=PASS`를 모두 확인해야 완료 보고 및 다음 Step 진입이 가능하다.
필수 실패·증거 누락·미실행·stale은 INCOMPLETE다. 수정 뒤에는 새 snapshot과 재검증이 필요하다.
검증 전 snapshot을 검증 후 새로 만들어 과거 결과를 현재 PASS로 바꾸지 않는다.

## 검증 절차

### 1단계: Awwwards 기준 스크린샷 수집

1. `step_archive/outputs/step024_검증_r1.md`의 최종 PASS manifest에서 채택한 기존·보충 원문과 이미지의 정확한 경로·SHA-256·통합 조사 축으로 비교 목록을 만든다. 기존 glob만으로 목록을 제한하지 않는다.
2. 경로를 해석하고 hash를 대조한 뒤 원문을 읽고 각 이미지를 직접 열어 수상작·화면·조사 축을 확인한다. 최종 PASS 누락, 입력 누락·hash 불일치 또는 필수 이미지 미검사는 INCOMPLETE다.

### 2단계: 구현 스크린샷 촬영

1. 개발 서버를 실행한다.
2. 브라우저 자동화 도구(docs/BROWSER-TOOLS.md 절차표)로 주요 뷰포트별(데스크톱, 태블릿, 모바일) 스크린샷을 촬영한다 (Aside 백엔드는 탭 고정 1440×900 — 실제 캡처 크기를 기록).
3. `step_archive/screenshots/compare-impl-desktop.png`, `compare-impl-tablet.png`, `compare-impl-mobile.png` 로 저장한다.

### 3단계: 비교 검증 루프

#### 3-1. 에이전트 B의 역할 (검증)

**에이전트 B에게 최종 Step 24 보고서와 manifest에서 만든 전체 비교 목록을 전달한다. B는 보고서를 직접 읽고 통합 분석·조사 축 및 모든 기존·보충 입력의 경로·hash를 대조한 뒤 각 채택 이미지에 대해 다음을 반복한다:**

1. Awwwards 스크린샷을 Read한다.
2. 구현 스크린샷을 Read한다.
3. 다음 여덟 축을 viewport마다 비교하고 **판정만 수행한다**. 비교 기준은 인상이 아니라 step030 설계가 최종 manifest의 조사 축에서 채택한 결정이다:
   - **레이아웃 구조**: 설계가 채택한 조사 패턴의 영역 분할·배치·비율이 구현에 있는가
   - **시각적 계층**: 설계가 정한 제목·본문·부가정보의 크기·굵기·색 계층이 화면에서 구분되는가
   - **여백/간격**: 간격이 설계 값 또는 허용 배수(4·8·16·24·32px) 안에 있고 같은 역할 요소끼리 같은가
   - **색상/대비**: 채택 팔레트 밖 색이 없고 본문 대비가 WCAG AA(4.5:1) 이상인가
   - **컴포넌트 완성도**: 버튼·카드·패널이 설계가 정한 상태(hover·focus·active·disabled)를 모두 갖췄는가
   - **컨트롤 패널 배치**: 설계가 조사 근거로 정한 위치에 있는가
   - **시각화 영역 비율**: 설계가 정한 메인 영역 비율 또는 최소 크기를 viewport마다 지키는가
   - **반응형 전환**: 설계의 breakpoint마다 배치가 설계대로 바뀌고 겹침·잘림·가로 스크롤이 없는가
   설계가 채택하지 않은 참고 이미지의 요소는 필수 기준이 아니다.

4. **판정 결과:**
   - 실제 검사한 기존·보충 입력의 경로·SHA-256, 조사 축과 구현 화면의 대응을 QA 증거에 기록한다.
   판정 규칙:
   - 필수 finding(`Critical`/`Important`): 설계 명세·선택 토큰·필수 acceptance를 어긴 것, 또는 기능·접근성 결함(겹침·잘림·가림·조작 불가 포함)
   - `advisory`: 어긴 기준을 인용할 수 없는 미관·선호 의견. advisory만 남으면 PASS이며 수정 대상이 아니다
   - 필수 finding마다 네 필드를 모두 쓴다:
     - 위치: 소스 `file:line`, 또는 route·viewport·selector·스크린샷 파일과 영역
     - 기준: 어긴 명세·토큰·acceptance의 출처(파일과 절 또는 줄)
     - 기대/관찰: 기대값과 관찰값(예: gap 24px 기대, 40px 관찰)
     - 재현: 같은 화면을 다시 보는 route·viewport·선행 조작
   - **PASS**: 여덟 축 모두 미해결 필수 finding 없음 → 해당 항목 종료. advisory는 따로 기록
   - **FAIL**: 필수 finding을 위 네 필드로 기록하여 에이전트 A에 전달

#### 3-2. 에이전트 A의 역할 (수정)

1. 에이전트 B의 FAIL 판정과 구체적 지적사항을 받는다.
2. **코드만 수정한다** (HTML/CSS/JS):
   - 에이전트 B가 지적한 필수 finding에 집중 (advisory는 수정 대상이 아니다)
   - 설계가 채택한 조사 패턴에 맞춘다
3. 스크린샷 재촬영
4. 재촬영한 스크린샷을 에이전트 B에 전달

#### 3-3. 반복 제한: 최대 5라운드

최대 5라운드까지 수정·재검증한다. 같은 필수 항목이 3연속 미수정이면 조기 종료한다.
모든 필수 항목의 현재 증거가 PASS일 때만 완료한다. 실패·누락·미검증 또는 한도 소진이면
미해결 항목과 다음 검사를 기록하고 현재 Step을 INCOMPLETE로 인계한다.
필수 실패를 스킵하거나 완료 보고 후 다음 Step으로 진행하지 않는다.
한도 소진이나 같은 필수 항목의 연속 미수정으로 끝나면 `required-input-missing`, 필수 실행·시각 검사 기능이 없으면 `required-tool-failed`로 헌법 §2-1 명명된 멈춤을 기록하고 턴을 끝낸다.

## 통과 조건

- 여덟 비교 축 모두에서 미해결 `Critical`/`Important` finding이 없다 (advisory는 보고서에 따로 남는다)
- 필수 finding은 모두 위치·기준·기대/관찰·재현과 함께 기록됐고 재검증에서 [수정됨]으로 확인됐다
- 채택한 기존·보충 입력을 모두 경로·SHA-256으로 대조했다

합리적인 선에서 최대한 많은 서브에이전트를 병렬로 사용한다 (동시 실행 최대 10개).

- **에이전트 B (검증)**: sonnet 사용 - 스크린샷 비교·분석 담당
- **에이전트 A (수정)**: sonnet 사용 - 코드 수정 담당
